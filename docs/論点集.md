## B. 未解決の論点（確認が必要）

### B-1【要確認・SBOAI】PaaSはライブラリ／SBOMまで見るのか
レビューで最も重い指摘。**「ライブラリの中身はわかりません」であれば、正直あまり使えない」**との評価。

- ソースコード診断の対象に、外部から取り込んだOSSライブラリの構成・脆弱性が含まれるか
- SBOM（ソフトウェア部品表）を出力できるか、あるいは顧客提供のSBOMを取り込めるか
- 現在のLPでは「利用ライブラリの構成まで確認する」を**顧客側が備えるべき観点**として書いており、PaaSの機能として断定していない。機能として言えるなら訴求の柱になる

### B-2【要注意・事実誤認】SBOMは法的義務ではない
レビュー中に「今年からガイドラインで作らなきゃいけなくなっている」との発言があったが、**確認したところ国内にSBOM作成の法的義務は存在しない**。

- 経産省「SBOM導入に関する手引」：2023年7月策定／2024年8月改訂（義務ではなく手引）
- 2026年7月30日：経産省・国家サイバー統括室がCISAの国際ガイダンスへ共同署名
- EU CRA：2027年から段階適用（EU市場向け製品）
- → LPでは「法的義務はないが取引条件としての要求は強まる」と正確に記載した。**対外説明でも義務と言わないこと**

### B-3【要ヒアリング・MUFG】勘定系の実態
- 勘定系の技術構成（COBOL／メインフレームの現況）
- クラウンジュエルとして何を定義しているか。CRM・顧客情報基盤の位置づけ

- Tier 0／PIM・PAMの整備状況

### B-4【要調査】NICT「NIRVANA」との競合関係
重要インフラ向けにNICTのサイバーセキュリティ可視化基盤が展開される可能性。量子計算基盤を用いる領域では正面から競合しても勝ち目が薄い。

## C. 業界選定の論点

### C-1 金融は「メガバンク」より「地銀」
- メガバンクは既存ベンダー（IBM等）との関係が確立しており、広告 → LP → 申込という動線に乗りにくい
- 地銀は共同センター依存でエンジニアが不在。要請は降りてくるが自前の対応手段を持たない
- **ただし本モックはメガバンク前提で作成済み。地銀版へ転用する場合、勘定系の記述（自前保有 → 共同センター利用）とクラウンジュエルの構成を差し替える必要がある**

#### C-1b【対応済み】地銀版 `regionalbank.html` を追加（2026-08-28）

メガバンク版は残し、7業界目として追加した。差し替えた論点は以下。

| 論点 | メガバンク版 | 地銀版 |
|---|---|---|
| 勘定系 | 自前保有・クラウンジュエルの候補 | **共同利用型の基幹システム＝自行の管掌外**。図の②は「自行の守備範囲＝接続点の手前」に変更 |
| リスク05（修復が止まる）の因果 | 24時間365日止められないから直せない | **直せる人が自行にいない**（情シス小規模・セキュリティ専任は数名か兼務）。PaaS訴求への接続はこちらのほうが強い |
| 侵入口① | 委託先・取引先 | 地場の委託先・システム子会社（本体と同水準を求めにくい取引関係） |
| 侵入口③ | 外部公開サーバー | IB・アプリ・**オープンAPI（電子決済等代行業者との接続）**。接続先の規模を自行が選べない |
| 感染拡大の固有条件 | ― | **統合・アライアンスの継ぎ目**（旧行システム併存、棚卸されない権限）を図の②に追加 |
| 波及先 | 取引先金融機関／決済／清算／社会機能 | **共同センター参加行／自治体の収納・給付／給与振込・年金支給／地域経済**（＝代替が存在しない） |
| キーメッセージ | クラウンジュエルは勘定系とは限らない | **勘定系が無事でも、営業店端末が全滅すれば窓口は開かない** |

判断したこと：

- **「1,800システム中1,100が外部管理」は地銀版から外した。** これはソフトバンクの自社診断の数値であり、図中で「委託先・外部ベンダー」の直下に置くと**その銀行自身の数値と誤読される**。地銀では桁が合わず、その場で信頼を失う。第2章 prem からも削除し、定性表現に置き換えた
- **事例は既存の検証済み定数を再利用した。** 巻末の免責が「原則1年以内、長くとも3年以内」と定めているため、構造的には最適だった大阪の医療機関の事案（2022年10月・給食委託事業者のVPN経由）は期間外となり不採用。同型の `VPNCASE`（2026年／国内医療機関・保守用VPN経由）で代替した
- **2023年10月の国内資金決済基盤の障害を、リスク05に追加した。** サイバー攻撃ではない旨を本文と巻末の両方に明記したうえで、「自行に原因がなくても共同利用型基盤の事故で業務が止まる」構造の実例として使用している

未確認（本文では具体数値を避けている）：

- 共同センターの構成・参加行数（NTTデータ、日本IBM、日立、富士通、NEC 各系統）
- 地銀の情報システム部門／セキュリティ専任の人員規模。「数名か兼務であることが多い」と定性で記述しており、**数値を入れる場合は出典が要る**
- ターゲット行の共同センター系統。系統によって責任分担の書きぶりが変わるため、個別提案時には確認が必要

#### C-1c【対応済み】電力版を、金融2版で得た型に合わせて改訂（2026-08-28）

メガバンク版・地銀版で整理した「**本体は自社が手を入れられない。守れるのはその手前**」という型を、電力版にも適用した。3業界で因果が揃う。

| 業界 | 本体に手を入れられない理由 | 守備範囲 |
|---|---|---|
| メガバンク | 24時間365日止められない | 顧客情報基盤・Tier 0・仮想化／バックアップ |
| 地方銀行 | 共同利用型＝自行の管掌外、かつ直せる人が自行にいない | 行内AD・営業店端末・情報系 |
| 電力会社 | **止められず、かつ機器ベンダーの領域** | **IT／OT境界とその手前**（共通AD・管理端末・仮想化／バックアップ） |

電力版の変更点：

- **図の②を「制御系（OT）」から「自社の守備範囲」に変更した。** 従来は従業員端末から制御系へ矢印が直接刺さる構図で、**OTがネットに直結しているかのように読め、OT側の実務者から「分かっていない資料」と判断されるリスクがあった**。`IT ／ OT 境界`（保守回線・可搬媒体・DMZ）を独立した層として図に出し、制御系は「止められない／ベンダー領域・触れられない」として図の外縁に置いた
- 本文（サマリー1-2）は以前から「最大の隙間はIT系とOT系の境界にある」と書いていたが、**図がそれを示していなかった**。図と本文の主張を一致させた
- **リスク06に「出口は2種類ある」を追加した。** 従来は情報の持ち出し（イグレス）から広域停電への波及が一続きに読め、論理が繋がっていなかった。持ち出しは通信プロトコル単位、影響の波及は系統連系・広域機関経由であり別経路であること、OTで問われるのは持ち出しより可用性と完全性であることを明記した
- **リスク05の見出しを「制御系が無事でも、運用は止まる」に変更した。** 地銀版の「勘定系が無事でも、窓口は開かない」と同型
- **第2章冒頭に事業者区分の前提を明記した。** 発電・一般送配電を自社保有する構成を前提とし、小売主体の場合は②が需給管理システムと顧客情報基盤に置き換わる旨。中給指令所とOCCTO・JEPXを同一の図に並べている以上、この断りがないと事業区分によって刺さり方が逆になる

**未解決（SVGの構造上の制約）**：図では「イグレス（出口）→ 波及先」が1本の矢印で描かれており、*情報が出ていく口*と*影響が伝わる口*が視覚的に分離されていない。本文では2種類あると明記したが、図として分けるには第2章のSVG（`build.py` の `diagram()`）の構造変更が要る。Claude Designでの作り込み時に検討する。この制約は電力版に限らず全業界版に共通する。

#### C-1d【対応済み】化学版を改訂（2026-08-28）

電力版と同じ改訂に加え、化学固有の「重要資産が二層ある」構造を図に反映した。

- **図の②を「プラント制御系」から「自社の守備範囲」に変更。** 従業員端末からDCS・PLCへ矢印が直接刺さる構図で、IEC 62443のゾーン分離を知る技術者には「分かっていない資料」と判定される。`IT ／ OT 境界` を独立層として出し、制御系は「止められない／DCSベンダー領域・触れられない」として外縁へ
- **`配合レシピ・プロセス条件` を図の主役に上げた（琥珀＝強調色）。** 本文サマリー3は以前から「生産は再開できるが、流出した技術情報は戻らない」と書いており、これは7業界で最も強い一行だが、**図では最下段のグレー（`dg-coremute`）に置かれていた**。主張と表示を一致させた
- **安全計装（SIS）を図の核から外した。** DCS・PLCと一続きに積むと「SISは独立させていない前提か。うちは分けている」と反論される。IEC 61511では基本制御系からの独立が原則。リスク05の対策を「SISは独立が原則であり、**その独立性が現に保たれているかを診断対象にする**」に書き換えた。反論される論点を、診断の必要性を示す論点に転換している
- **リスク05の見出しを「プラントは再開できるが、レシピは戻らない」に。** メガバンク／地銀／電力と同じ型
- **prem③で「外へ波及するもの」と「内に残る回復不能な損失」を切り分けた。** 技術情報の流出は外部への波及ではなく自社に残る損失であり、指標も対策も別である旨
- ins③の3行目が `公開系・内部ライブラリ`（リモート保守の説明と噛み合わない他業界テンプレの流用）だったため `常時接続・公開系ライブラリ` に修正

**判断したこと**：TRITON／TRISIS（2017年・中東の石化プラント）は巻末の「原則1年以内、長くとも3年以内」の対象外だが、**改訂前から巻末の出典に理由付きで記載されていたため、そのまま残した**。SISを直接狙った事例は他に代替がなく、除外すると保安側の論拠が消える。

**改訂状況（7業界）**：メガバンク／地銀／電力／化学の4版に「本体は触れない・守備範囲はその手前」の型を適用済み。**航空・物流・情報通信の3版は未適用**。

#### C-1e【対応済み】全7業界で、侵入口の主役を「外部に露出したサーバーの脆弱性」に変更（2026-08-28）

**変更の理由（訴求とPaaSの整合）**：改訂前の侵入口は、委託先アカウントの窃取・多要素認証の未設定・フィッシングが主役だった。**これらの手当てはIDaaS・MFA・EDRであって、PaaS（脆弱性の診断と修復）ではない。** 脅威の物語が、売っているものと噛み合っていなかった。侵入口を外部露出資産の既知脆弱性に寄せることで、ブラックボックス診断 → 修正 → 仮想パッチという対策列が、そのままPaaSの機能列になる。

事実の面でも寄せる方が正確で、ランサムの初期侵入は境界機器・公開資産の脆弱性が最大勢力である（**警察庁の統計での構成比は要確認。本文では数値を出していない**）。

全7業界に一律で適用した内容：

- **図の①を3枚とも入れ替え。** 先頭を `外部に露出したサーバー ／ [業界固有の公開資産] ／ 既知の脆弱性が未修正のまま` に統一し、旧①（委託先・取引網＝IPA 2位タグ付き）を2番目、従業員端末を3番目に繰り下げ
- **第3章のリスク順序を入れ替え。** 旧リスク03（公開系＋ライブラリ）を **リスク01** へ昇格、旧01（委託先・取引網）を02、従業員端末を03に。見出しも全7本を `外部に露出したサーバーの既知脆弱性──…` で始まる形に統一した
- **第2章 prem① を全7業界で書き換え。** 「最初に狙われるのは、外部に露出したサーバーと機器である」で始め、業界固有の露出資産を挙げたうえで、業界固有の接続先（取引網・共用基盤・協力会社など）へ話を広げる構成に
- 図のアクセシビリティ説明（`desc`）も7本すべて更新

**IPA 10大脅威 2位（サプライチェーン）の扱い**：図の2番目とリスク02に残しており、権威付けは維持している。侵入口の主役を移しただけで、論拠を捨ててはいない。

#### D-1【対応済み・既存不具合】サマリーと第2章 前提で `<strong>` が literal 表示されていた

`summary()` と `diagram()` の本文が `E(p)`（HTMLエスケープ）を通っており、`build.py` の `sum` / `prem` に書かれた `<strong>` タグが `&lt;strong&gt;` としてそのまま画面に出ていた。**化学・航空・物流・情報通信の4版で発生していた既存不具合**（例：化学サマリー3「生産は再開できるが、流出した技術情報は戻らない」）。

| 領域 | 評価 | 理由 |
|---|---|---|
| 医療 | **有力** | 厚労省の関与が強く、電子カルテ停止が人命に直結。国内事例も取りやすい |
| 金融（地銀） | **有力** | 金融庁の枠組みが多く、要請の流れに乗せやすい |
| 公共 | **要注意** | ガバメントクラウドが進行中。「ガバメントクラウドがあるので」で跳ね返されるリスク。提案にはガバメントクラウド側の知見が必要 |

### C-3 B2Bのインシデントは非公表が多い
公開される事例はB2C（個人情報漏えい）に偏る。B2B主体の業界を選ぶと、訴求に使える一次情報が集まりにくい。**事例の入手可能性を業界選定の基準に含める必要がある。**

## D. LP形態の論点

### D-1 現状は「論文」に寄りすぎている
指摘：**電車の中で見るものとしては難読。論文として読み込む形になっている。**

- ターゲットは年商300億円以上。ただし2000億円以下の層には専門用語が通じない
- 「PaaS」という名称自体が一般的なPlatform as a Serviceと混同される。**Patching as a Service であることを明示しないとスルーされる**

### D-2 セキュリティカオスマップ形式への転換
指摘された方向：
- 侵入口のマップがずらりと並ぶ
- 中身では Tier 0 が乗っ取られ、感染が各部位へ転移していく様子が見える
- 出口がアイコンで並ぶ
- 到達すべき読後感は「**こんなにリスクがあるのか。自社ではハンドルできない。一旦PaaSに任せよう**」

→ **一度カオスマップ（キーワード93項目）を試作したうえで、構成図の形式に差し戻した。**カオスマップは量の圧を出せる一方、「どこから入られ、どこへ抜けるか」という流れが読み取れず、リスク詳細（第3章）との対応も付きにくかったため。現行は侵入口→感染拡大→持ち出し口を1本の流れで見せる構成図に戻している。視覚的な作り込みは Claude Design に依頼（`docs/claude-design-prompt.md`）。

なお、カオスマップ試作時に洗い出した直近1年の侵入口キーワード（GitHub管理アカウント／npmパッケージ乗っ取り／SIer経由の侵害／連携外部アプリの設定不備 ほか）は、各業界版のリスク詳細に事例として取り込んでいる。

### D-3 訴求の型
「8割のリスクを一括で解消できる」という**減算の訴求**が、専門用語を並べるより効く可能性がある。カオスマップで全体量を見せたうえで、PaaSがカバーする範囲を塗る構成。
